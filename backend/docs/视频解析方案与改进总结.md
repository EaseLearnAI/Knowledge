# 视频解析方案评估与改进总结

## 最终采用的路线

采用“Node 产品服务 + 现有 Python 视频内核”的组合：

```text
Express API
  → MongoDB 保存 SourceItem 与 ProcessingTask
  → 串行任务队列
  → videosummarize CLI / 本地上传桥接
  → FFmpeg
  → Whisper
  → 带时间戳 Transcript
  → 本地或 MiniMax 文案适配器
  → 收藏详情与 SSE 日志
```

没有复制或修改原 `videosummarize` 逻辑。URL 继续调用已验证 CLI；本地上传通过后端新增的桥接文件复用其 `extractor` 与 `transcriber`。

## 为什么这样选

对指定目录的三个方案评估后，结论与原评估文档一致：

- `videosummarize` 最适合做音视频采集和转录能力；
- `cliskill` 的 Python 源码是当前可运行内核；
- 它们不应直接承担用户、鉴权、MongoDB、任务 API 和多端同步；
- Node 后端应把这套内核包装成稳定、可观察、可替换的服务。

## 已完成的关键改进

- URL 转录显式使用单路 Whisper，避免低可用内存环境下多个 MLX 分块并发导致进程异常退出；跨任务仍由 Node.js 串行队列控制。

| 原能力 | 新增改进 |
|---|---|
| CLI 同步执行 | `202 Accepted` 异步任务 |
| 只在终端显示 | Mongo 日志 + 任务 SSE + Web 终端 |
| transcript 文件 | 统一 `SourceItem`、毫秒时间戳证据 |
| 无账号 | 注册、登录、JWT、刷新令牌轮换 |
| 无幂等 | 用户 + `Idempotency-Key` 唯一索引 |
| MLX 可能并发崩溃 | 服务端视频任务严格串行 |
| 只转录 | 自动生成摘要、观看价值、关键点、章节、动作、Tag、Markdown |
| 文案依赖 Agent 临时发挥 | `Copywriter` 接口，local/MiniMax 可切换 |
| 失败只输出文字 | 持久化错误码和原始阶段日志 |
| 无前端契约 | OpenAPI + 中文 API 文档 + TypeScript 接入示例 |

## 文案承接设计

客户端无需再拼接文案，直接读取：

- `oneSentenceSummary`：卡片和详情首屏；
- `whyWorthWatching`：解释收藏价值；
- `keyPoints`：3–7 条重点；
- `chapters`：章节与时间戳；
- `actionItems`：可以继续执行的动作；
- `tags`：列表筛选；
- `markdown`：分享、导出或富文本渲染。

默认 local 适配器确保没有模型 Key 时所有接口仍可用。MiniMax 通过 OpenAI 兼容接口增强文案质量，当前默认模型为 `MiniMax-M3`；切换同一接口下的模型只改环境变量，不改路由和前端结构。

## 真实验证

已覆盖：

1. `videosummarize doctor`：FFmpeg、yt-dlp、mlx-whisper、faster-whisper 可用；
2. 本机合成中文语音；
3. FFmpeg 转 16 kHz 单声道音频；
4. 本地 Whisper 得到非空文本和时间戳；
5. HTTP 注册、鉴权、创建任务、完成任务、内容详情、删除；
6. 重复幂等键不产生第二个任务；
7. 弱密码、重复邮箱、错误密码、非法平台、未登录和错误 ID。

## 当前边界

- 当前机器没有常驻 MongoDB 可执行文件，正式本地服务需要安装 MongoDB；测试已用真实临时 MongoDB 完成。
- YouTube 和小红书可能依赖 Chrome 登录态；服务端部署到 Linux 时不能直接读取个人浏览器 Cookie，需要后续做受控授权或用户上传。
- `COPYWRITER_PROVIDER=minimax` 需要 `MINIMAX_API_KEY`。未提供时默认本地文案，不影响转录。
- 当前队列是单进程串行，符合本机 MVP 和 MLX 限制；多机部署应换为 Redis/BullMQ，并按设备/GPU 做并发锁。
- 当前原视频和音频转录后默认不长期保留，只保留转录结果，符合 PRD 当前假设。
